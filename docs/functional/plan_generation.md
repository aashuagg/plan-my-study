# Plan Generation — End-to-End Flow

## Overview

A weekly study plan is generated by combining student profile data, current curriculum topics, SM-2 review queue, and learning history into a structured prompt, which is sent to an AI model (Ollama or Claude). The AI returns a JSON schedule for the week.

---

## Data That Feeds Into the Prompt

### 1. Student Profile

```
- Name
- Grade (e.g., "UKG")
- Board (e.g., "CBSE")
- Daily study duration in minutes
- Study days per week (weekly_frequency)
- Subjects list
```

This determines: how many day slots to fill, how many minutes per day, and which subjects are valid.

### 2. Current Curriculum (New Topics)

Pulled from `curriculum_items` for the active newsletter period. Formatted as:
```
- LITERACY: Letter Recognition (starts 2026-05-01)
- NUMERACY: Counting to 20 (starts 2026-05-03)
```

Limited to the first **20 items** to prevent token overflow.

### 3. Topics Due for SM-2 Review

Topics from `learning_history` where `next_review <= today`. Formatted as:
```
- HINDI: Vowels (due: 2026-05-10, 3 days overdue, easiness: 2.3)
```

Ordered by **neglect, not raw due-date**: `get_due_topics()` sorts by `last_reviewed ASC
NULLS FIRST` (never-touched topics first) then `next_review ASC` as a tiebreak. A topic
reviewed a few days ago ranks below one that's been untouched for weeks, even if both are
technically "due" — see Issue 3 below for why this matters.

Limited to the first **30 items** (raised from 15 in Jul 2026) to keep prompt size bounded.

Topics with `graduated = TRUE` are excluded from this query entirely — see **Topic
Graduation** below.

#### Topic Graduation (Manual Mastery Override, added Sep 2026)

**Problem this solves:** `last_reviewed`-based neglect sorting has no way to stop a topic
from cycling back into the due queue forever, and SM-2's own interval growth
(`round(interval × EF)`) is uncapped, so a topic that's been reviewed for a year keeps
consuming review slots indefinitely. Since new curriculum arrives every month
(`docs/functional/newsletter.md`) but weekly capacity is fixed (max 2 topics/session × 6
sessions), the pool of "topics competing for a slot" only grows over time unless something
can permanently exit it.

**Mechanism:** a parent can mark any topic that's been reviewed at least once (`repetitions
> 0`) as **graduated** — a manual override, not an algorithmic one. `learning_history` gets
two new columns: `graduated` (bool) and `graduated_at` (date). `get_due_topics()` and
`get_overdue_topics()` (`backend/crud/analytics.py`) both filter `graduated IS FALSE`, so a
graduated topic stops appearing in the AI prompt and in the Progress Report's overdue list —
it never competes for a slot again unless un-graduated.

**Where it's set:** from "This Week's Plan" — see `docs/functional/progress_tracking.md` for
the UI flow and the undo path (Progress Report → Graduated Topics → Un-graduate).

**Deliberately no algorithmic gate:** graduation is entirely the parent's judgment call: no
minimum repetitions/EF/interval threshold is enforced beyond `repetitions > 0`. This mirrors
past guidance on this codebase to prefer parent-driven overrides over the algorithm
guessing at mastery.

**Reversible:** un-graduating clears `graduated`/`graduated_at` only — SM-2 fields
(`easiness_factor`, `interval`, `repetitions`, `next_review`) are untouched, so the topic
resumes exactly where it left off rather than restarting its spacing curve.

**Still true:** graduation only bounds the review-queue's *lower* bound (parent removes
topics they know are solid). It does not itself cap `next_review` growth for
non-graduated topics — an interval ceiling and overdue-ratio-based sorting (rather than
raw `last_reviewed` recency) were discussed as complementary fixes but are not yet
implemented.

### 4. Learning History Summary

A per-subject summary of topics that have been reviewed at least once (`last_reviewed IS NOT NULL`):
```
- LITERACY: 8 topics practiced, last session 2026-05-11 (2 days ago)
- HINDI: 5 topics practiced, last session 2026-05-08 (5 days ago)
```

Topics that have never been reviewed are excluded — they are "new" not "overdue".

### 5. Optional Parent Inputs

- **Focus request:** Free text, e.g. "Extra Hindi practice this week"
- **Upcoming events:** Free text, e.g. "Olympiad on May 20" or "Sessional exams Jul 21-23 —
  light revision only, no new topics"

**Availability (fixed Jul 2026):** these two fields previously only appeared on the very
first plan ever generated (`_show_plan_generation_form`, shown only when no plan exists
yet). Every subsequent week went through "🔄 Generate Next Week's Plan"
(`_generate_next_week`), which called the generator with both hardcoded to `None` — there
was no way to flag an exam week or an upcoming olympiad after the first plan. Both fields
now also appear (collapsed in an expander, so the common no-special-request case stays
uncluttered) above the action buttons on every week, and are cleared after a successful
generation so a one-off note doesn't silently reapply to the following week.

## SM-2 Scheduling Rules Embedded in the Prompt

The system prompt instructs the AI to:

| Rule | Detail |
|------|--------|
| **Prioritise due topics** | Topics with `next_review <= today` are due and should appear this week, in the neglect-first order they're listed in |
| **Review floor, not a fixed split** | Review is *at least* 20% of the week — not a fixed 60/40 ratio. The AI is told to lean further into review when the due-topics backlog is large relative to new curriculum. (Changed Jul 2026 — a fixed ratio couldn't adapt as the monthly backlog grew faster than weekly capacity.) |
| **No subject neglect** | No subject should go unreviewed for more than 7 consecutive days |
| **Subject frequency** | Every subject must appear at least 2 times during the week |
| **Even distribution** | Distribute subjects across the week; avoid consecutive same-subject days |

---

## Hard Constraints

These are enforced via explicit instructions in the user-facing prompt section (`_build_full_prompt`):

### 1. Maximum 2 Topics Per Day (ABSOLUTE)

```
ABSOLUTE HARD LIMIT: Maximum 2 topics per day, no exceptions.
It is CORRECT and EXPECTED to leave topics unscheduled.
Unscheduled topics automatically carry over to next week.
A plan with 2 topics per day is a PERFECT plan.
A plan with 3+ topics on any day is a FAILED plan.
```

### 2. Subject-Topic Matching

Every topic listed for a day must belong to a subject that also appears in that day's subjects list:

```
SUBJECT-TOPIC MATCHING RULE:
Each topic must belong to one of the subjects listed for that day.
Before finalising each day, verify: does every topic's subject appear
in that day's subject list?
```

### 3. No "Catch-Up Day"

```
The last day of the week follows the SAME rules as every other day.
There is no "catch-up" day. If week ends with unscheduled topics,
they move to next week.
```

### 4. No Invented Topics

```
ONLY use subjects and topics from the "Current Curriculum" and
"Topics Due for Review" sections. DO NOT invent, create, or make up
ANY subjects or topics.
```

### 5. Exact Topic Name Copying

```
Copy topic names EXACTLY as they appear in the curriculum data.
```

This is critical: if the AI paraphrases a topic name, it won't match the `learning_history` row, and the session cannot be saved.

## Output Schema

The AI is expected to return JSON matching:

```json
{
  "weekly_plan": [
    {
      "date": "2026-05-19",
      "subjects": ["LITERACY", "NUMERACY"],
      "topics": ["Letter Blending", "Counting to 20"],
      "is_new_topic": [true, false],
      "duration_minutes": 30
    }
  ],
  "rationale": "Hindi was prioritised because it was last practiced 5 days ago..."
}
```

The `JsonOutputParser` (LangChain) appends format instructions to the prompt to enforce this structure.

## How Ollama vs Claude Behave Differently

| Aspect | Ollama (llama3.2) | Claude (sonnet) |
|--------|-------------------|-----------------|
| **2-topic hard limit** | Frequently violated (3–4 topics per day common) | Reliably respected |
| **Subject-topic matching** | Often mismatches topics to wrong subjects | Consistently correct |
| **Topic name fidelity** | Sometimes paraphrases topics | Copies names exactly |
| **JSON format** | Uses `format="json"` mode to force structure; occasionally malformed | Clean JSON consistently |
| **Rationale quality** | Brief and generic | Detailed and specific |
| **Inference speed** | Fast (local, no latency) | Slower (network API call) |
| **Cost** | Free | Paid API |

**Workaround for Ollama violations:** Validate `plan_data` after generation — count topics per day and alert the parent if any day exceeds 2 topics. This validation is not yet implemented in the MVP.

## Known Issues and Workarounds

### Issue 1: Topic Name Mismatch

**Problem:** The AI generates a topic name like "Letter Blending" but the DB has "Blending of Letters". The `topic_lookup` in `weekly_plan.py` uses an exact `"{subject}|{topic}"` key and returns `None`. The topic gets `learning_history_id = None` and cannot be saved.

**Current workaround:** Sessions for unmatched topics are silently skipped with a UI message. The parent can note which topics were skipped.

**Planned fix:** Fuzzy matching on topic lookup; or enforce exact topic names at plan generation time with a stricter prompt.

---

### Issue 2: Ollama Ignoring the 2-Topic Cap

**Problem:** llama3.2 often schedules 3–4 topics per day despite the explicit hard limit instruction.

**Current workaround:** Use Claude (production) for reliable plans. When using Ollama, the plan must be reviewed manually before acting on it.

**Planned fix:** Post-generation validation that trims plans exceeding 2 topics per day and logs a warning.

---

### Issue 3: Due Topics Silently Dropped Past the Cap (Fixed Jul 2026)

**Problem:** `get_due_topics()` had no `ORDER BY`, and the due-topics formatter capped the list at 15 items. With 40+ topics due at once and many sharing the same `next_review` date (an entire newsletter batch initialized together), the arbitrary tie-break order pushed whole subject batches past the cutoff every week — they never became AI candidates at all. This is how a 7-topic Kannada batch and a Dictation topic went unscheduled for weeks without any error or warning.

**Fix:** `get_due_topics()` now orders by neglect (`last_reviewed ASC NULLS FIRST`, then `next_review ASC`), and the cap was raised 15 → 30. The Monthly Topics tab (Upload Newsletter page) was also added so newsletter + diary entries can be visually cross-checked against what actually appears in plans.

**Still true:** the curriculum formatter (`_format_curriculum`) still caps at 20 items with no ordering — the same failure mode could recur there if a single month's newsletter exceeds ~20 usable topics after cleaning. Not yet hit in practice; worth the same fix if it is.
